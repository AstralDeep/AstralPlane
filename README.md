# AstralPlane

## Overview

AstralPlane is a Python-based backend middleware designed to bridge the gap between user-facing frontends (like the web-based **AstralProjection**) and sophisticated agentic AI models, particularly those implementing the Model Context Protocol (MCP).

It functions as an intelligent intermediary, facilitating communication and data flow. AstralPlane handles both standard RESTful API interactions and real-time WebSocket streams. A key feature is its ability to pass information from the backend AI that drives not only the *content* but also the *visual rendering* on the frontend. **Visual primitives**, discovered or generated by the AI models (potentially via tool calling), are relayed through AstralPlane and pushed to the frontend (like AstralProjection) for dynamic UI generation, enabling a truly **AI-driven UI**.

This manages connections and translates requests between the frontend client and one or more backend MCP servers or other AI/agentic models, serving as the engine powering the dynamic frontend experience.

## Key Features

* **Middleware Architecture:** Acts as a central hub connecting frontends (like AstralProjection) and AI/MCP backends.
* **Hybrid Communication:** Supports both standard RESTful APIs (for operations like authentication, project management) and WebSockets (for real-time AI interaction streams and UI updates).
* **MCP Integration:** Natively designed to interact with AI models and servers using the Model Context Protocol (MCP). Includes client logic and connection management for MCP endpoints.
* **AI-Driven UI Control:** Generates and transmits UI definitions (as nested **primitives**) and real-time updates to the frontend via WebSockets, enabling dynamic and context-aware user interfaces consistent with the AstralProjection frontend concept.
* **Real-time Data Streaming:** Leverages WebSockets for low-latency communication, sending messages like `initial_ui_state`, `primitive_content_update`, `mcp_progress`, and `tool_schemas` to the frontend.
* **Action Handling:** Receives `ui_action` messages from the frontend via WebSockets, triggering corresponding backend processes or AI interactions.
* **Authentication & Authorization:** Secures endpoints using token-based authentication.
* **Project Management:** Provides APIs to organize work or sessions into distinct projects.
* **Asynchronous Processing:** Built using FastAPI and asynchronous libraries for efficient handling of concurrent connections and I/O operations.

## Examples
We have included a few example implementations of the MCP servers in the `mcp_servers` directory. These are mock implementations of the Model Context Protocol (MCP) using AstralPlane as the middleware. You can run one or multiple servers at the same time.

To run one of the example servers (in this case, `mcp_servers/mcp_async_demo.py`, follow these steps:
1. Make sure you have activated your virtual environment.
2. Start one (or all) MCP server(s):
    ```python -m app.mcp_servers.mcp_async_demo```
3. In a separate terminal, start the AstralPlane server:
    ```python -m app.main```
4. You may also want to start the AstralProjection frontend to see the UI in action. Follow the instructions in the AstralProjection repository to set it up.

AstralPlane now supports dynamic loading of servers into the system. Once you have both of the above Python files running, you can interact with the REST API endpoints to add or remove an MCP server. See below.

### 1. Create New MCP Server Configuration

Registers a new MCP server configuration in the system.

- **Endpoint:** `POST /`
- **Success Status Code:** `201 CREATED`
- **Response Model:** `MCPServerConfigResponse`
- **Description:** Adds a new MCP server. The `id`, `name`, and `url` must be unique.

**Request Body:**

- **Content-Type:** `application/json`
- **Schema:** `MCPServerConfigCreate`
  - `id` (string, required): A unique client-provided identifier for the server.
  - `name` (string, required): A unique descriptive name for the server.
  - `url` (string, required): The unique URL endpoint for the server's SSE (Server-Sent Events) stream.
  - `description` (string, optional): A more detailed description of the server.
  - `is_active` (boolean, required): Whether the server configuration is currently active.

**Example curl command:**

```bash
curl -X POST http://localhost:8000/api/mcp-servers/ \
-H "Content-Type: application/json" \
-d '{
  "id": "mcp_async_demo",
  "name": "Async Demo Server",
  "url": "http://127.0.0.1:8123/sse",
  "description": "Demonstrates various asynchronous notifications.",
  "is_active": true
}'
```

**Responses:**

- `201 CREATED`: Server configuration created successfully. Returns the created server configuration.
- `400 BAD REQUEST`:
  - If an MCP Server with the provided id already exists.
  - If an MCP Server with the provided name already exists.
  - If an MCP Server with the provided url already exists.

### 2. Get All MCP Server Configurations

Retrieves a list of all MCP server configurations, with support for pagination and filtering by active status.

- **Endpoint:** `GET /`
- **Success Status Code:** `200 OK`
- **Response Model:** `List[MCPServerConfigResponse]`
- **Description:** Fetches MCP server configurations.

**Query Parameters:**

- `skip` (integer, optional, default: 0, min: 0): Number of records to skip for pagination.
- `limit` (integer, optional, default: 100, min: 1, max: 500): Maximum number of records to return.
- `only_active` (boolean, optional, default: None): Filter by active status. If true, returns only active servers. If false, returns only inactive servers. If not provided, returns all servers.

**Example curl commands:**

Get all servers (default skip 0, limit 100):
```bash
curl -X GET "http://localhost:8000/api/mcp-servers/"
```

Get first 5 servers:
```bash
curl -X GET "http://localhost:8000/api/mcp-servers/?skip=0&limit=5"
```

Get only active servers:
```bash
curl -X GET "http://localhost:8000/api/mcp-servers/?only_active=true"
```

Get inactive servers, skip 0, limit 10:
```bash
curl -X GET "http://localhost:8000/api/mcp-servers/?skip=0&limit=10&only_active=false"
```

**Responses:**

- `200 OK`: Successfully retrieved the list of server configurations. Returns a list of server configurations (can be empty).

### 3. Update MCP Server Configuration by ID

Updates an existing MCP server configuration identified by its string ID.

- **Endpoint:** `PATCH /id/{server_id}`
- **Success Status Code:** `200 OK`
- **Response Model:** `MCPServerConfigResponse`
- **Description:** Modifies attributes of an existing MCP server.

**Path Parameters:**

- `server_id` (string, required): The string ID of the MCP server configuration to update.

**Request Body:**

- **Content-Type:** `application/json`
- **Schema:** `MCPServerConfigUpdate` (All fields are optional. Only provided fields will be updated.)
  - `name` (string, optional): The new name for the server. Must be unique if changed.
  - `description` (string, optional): The new description for the server.
  - `url` (string, optional): The new URL for the server. Must be unique if changed.
  - `is_active` (boolean, optional): The new active status for the server.

**Example curl command:**
```bash
curl -X PATCH http://localhost:8000/api/mcp-servers/id/mcp_async_demo \
-H "Content-Type: application/json" \
-d '{
  "name": "Async Demo Server (Updated Name)",
  "description": "This server has an updated description and is now inactive.",
  "url": "http://127.0.0.1:8123/sse",
  "is_active": false
}'
```

**Responses:**

- `200 OK`: Server configuration updated successfully. Returns the updated server configuration.
- `404 NOT FOUND`: If no MCP Server configuration with the given server_id exists.
- `409 CONFLICT`:
  - If the new name provided already exists for another server.
  - If the new url provided already exists for another server.
- `500 INTERNAL SERVER ERROR`: If the update operation failed unexpectedly in the database.

### 4. Delete MCP Server Configuration by ID

Deletes an existing MCP server configuration identified by its string ID.

- **Endpoint:** `DELETE /id/{server_id}`
- **Success Status Code:** `200 OK`
- **Response Model:** `Dict[str, str]` (A message confirming deletion)
- **Description:** Removes an MCP server configuration from the system.

**Example curl command:**
```bash
curl -X DELETE http://localhost:8000/api/mcp-servers/id/mcp_async_demo
```

**Responses:**

- `200 OK`: Server configuration successfully deleted. Returns a confirmation message.
  - Example: `{"message": "MCP Server 'Old Name' (ID: mcp_mock_chatviewbasic) successfully deleted and manager notified."}`
  - If manager notification fails: `{"message": "MCP Server 'Old Name' (ID: mcp_mock_chatviewbasic) deleted from DB, but manager notification encountered an issue."}`
- `404 NOT FOUND`: If no MCP Server configuration with the given server_id exists.
- `500 INTERNAL SERVER ERROR`: If the deletion failed in the database.



## Configuration

Application settings are managed in `app/config.py`. Key configurations likely include:

* `DATABASE_URL`: The connection string for the primary database.
* `SECRET_KEY`: A secret key for signing tokens and security purposes.
* `ALGORITHM`: The algorithm used for JWT token encoding (e.g., `HS256`).
* `ACCESS_TOKEN_EXPIRE_MINUTES`: Expiry time for access tokens.
* `MCP_SERVER_URLS`: Endpoint addresses for the backend MCP servers or AI models.

It is recommended to use environment variables for sensitive information like `DATABASE_URL` and `SECRET_KEY` rather than hardcoding them.

## API Endpoints

* `/api/auth`: Authentication related endpoints (e.g., `/token` for login).
* `/api/projects`: CRUD operations for managing projects.
* `/api/ws/stream/{project_type}:{project_id}`: WebSocket endpoint for real-time communication between the frontend (e.g., AstralProjection) and the backend AI via AstralPlane. Requires authentication token as a query parameter (e.g., `ws://.../api/ws/stream/mcp:myproject?token=YOUR_TOKEN`).
* `/api/mcp-servers`: Endpoints for managing MCP servers (e.g., adding, removing, listing active servers).

Refer to the auto-generated API documentation (`/docs` or `/redoc`) for detailed endpoint specifications and request/response models.

## WebSocket Communication (with AstralProjection) OLD!!!

AstralPlane communicates extensively with the frontend via WebSockets to enable the dynamic, AI-driven UI:

* **Connection**: Established after successful authentication and project selection on the frontend, using the authenticated WebSocket endpoint.
* **Key Messages Sent by Backend:**
    * `initial_ui_state`: Defines the entire initial UI structure using nested primitives. Sent upon connection or when the AI decides a full UI refresh is needed.
    * `tool_schemas`: Provides schemas for tools the AI might use or reference, potentially for frontend display or validation.
    * `primitive_content_update`: Updates the content or state of specific UI primitives (e.g., appending text to `StreamingTextView`, updating `LogView`, clearing an `InputField`, adding items to `ChatViewBasic`). Specifies the `targetId` of the primitive to update.
    * `mcp_progress`: Sends progress updates from backend MCP processes or long-running tasks.
    * `mcp_notification`: General status notifications from the backend or AI agents.
    * `error`: Indicates an error occurred during backend processing, potentially displayed to the user via a frontend notification mechanism.
* **Key Messages Received from Frontend:**
    * `ui_action`: Sent when the user interacts with an actionable primitive (e.g., `Button`). Contains `actionId` (identifying the backend action to perform) and `arguments` (often derived from the state of other primitives like `InputField`, identified by `valueSourceElementIds` in the Button's config).

### Core Functionality

#### Generating UI Primitives

* This is a critical part. The code shows how to create Python objects (likely Pydantic models defined in `app/models/schemas.py` or similar) that represent the visual elements AstralProjection can render. Examples include:
